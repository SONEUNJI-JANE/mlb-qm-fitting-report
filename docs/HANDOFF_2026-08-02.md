## 오늘 고친 것 (xlsx_source.py)

1. **회차(round) 판정 버그** — `_latest_round()`. 접수/전달/피팅 칸에 날짜 대신 메모 텍스트(예: "두 업체 모두 전달 완료", "전 회차 승인 완료", "넥목업")가 들어있는 셀을 진짜 회차로 오판해서, 실제 데이터 있는 이전 회차를 덮어쓰던 버그. "피팅" 칸은 날짜 아닌 메모가 들어갈 수 있어서 판정 기준에서 뺐고, 접수/전달일은 `isinstance(x, datetime)`로 실제 날짜인지 검사하도록 고침.
2. **Approved인데 전달일(확정일) 칸만 빈 경우** — 피팅일로 confirm_date 폴백 처리.
3. **라벨-오프셋 매칭 버그** — `compute_label()`. WOVEN/DENIM 품목엔 원래 "3천장이하" 구간이 없는데(기준표 11줄 중 WOVEN 2줄·DENIM 1줄만 있고 전부 "일반"), 수량 3천장 이하면 무조건 "3천장이하" 라벨을 붙여서 69개 스타일이 기준표 매칭 자체가 안 되던 버그. KNIT/SWEATER만 수량 구간 적용하도록 고침.
4. **DENIM인데 논워싱으로 찍힌 예외 케이스** — 기준표에 DENIM워싱일반 한 줄뿐이라 매칭 폴백 추가(`_offset_lookup_label`). 단, 실제로 확인해보니 이 케이스(3FDPG4066, 3FDPM4066)는 RAW(Apparel)에 BU=0/qty=0/ETD=None인 미입력 placeholder 행이라 이 폴백 자체는 지금 실효과 없음.

## 오늘 고친 것 (report_builder.py, 분석탭 JS)

1. 디자인 피드백 6건 반영 (필터 드롭다운화+표에 통합, 완료율 라인차트 삭제, 도넛 6개 분할, 초과일수 FIT/PP/TOP 드롭다운, 카운트 표시 등).
2. **"완료"(Due Date 기준) 계산에 no-due-but-done 케이스 포함** — due date를 못 구했어도 이미 완료된 건은 "완료"로 잡히게(`computeProgressFromRaw`, `analysisStats`의 `isDue` 판정에 `|| (!due && isDone)` 추가). 안 그러면 라벨/ETD 누락된 스타일이 통계에서 조용히 빠짐.
3. **"주별 정시 승인율" 표 전면 재설계** (`dueDateRecordsByStage`, `dueDateOnTimeComplianceByStage`, `withCumulative`):
   - 주차별(고정값) = 그 주 due였던 것 중 due 이내 승인된 비율. 실제 due 있는 것만(no-due-but-done 섞으면 그 주에 진짜 일어난 일이 아닌데 카운트 부풀려짐 — 이거 한 번 잘못 만들어서 W31에 26건 잘못 뜬 적 있음).
   - 누적 = **승인이 실제로 일어난 시점 기준**으로 따라잡으며 채워짐(due 기준이 아님). 밀렸던 게 나중에 승인되면 승인된 주차의 누적에 반영됨. no-due-but-done 케이스는 기준일 시점에 누적에 합류.
4. **정시 판정에 `isDone` 체크 누락 버그 발견, 수정 시작하다가 중단** — 아래 "미해결" 참고.
5. sec1(단계별 Due Date 달성률) 도넛 왼쪽=완료 기준 누적, 오른쪽=정시 승인율 누적(아래 표 최종 행과 같은 숫자 쓰도록 수정) — **이 수정은 JS 문법검증/테스트/재배포를 안 한 채로 세션이 끝남. 배포 안 됨.**

## 미해결 — 내일 여기부터 (2026-08-02 세션 마지막에 사용자가 방향 확정함)

### 1. (제일 중요, 메인 수정사항) "누적" 컬럼을 훨씬 단순한 로직으로 교체

**사용자 최종 결정** (그대로 따를 것, 재질문 불필요):
- **주차별 컬럼은 그대로 둔다.** 이건 "정시 승인율"이 맞다 — 그 주 due였던 것 중 due 이내에 승인된 비율, 영구 고정(나중에 승인돼도 그 주차 숫자 안 바뀜). 코드 안 건드림 (`dueDateOnTimeComplianceByStage`, `dueDateRecordsByStage`의 due-있는 케이스 로직 그대로).
- **누적 컬럼은 "정시" 개념을 뺀다.** "승인이 실제 일어난 시점 기준으로 따라잡는" 캐치업 로직(confirmPeriod 기준 집계) 필요 없음 — **삭제**. 대신 메인탭 "Due Date 기준"과 완전히 같은 로직(그냥 `isDone`이냐만 보는 단순 완료 여부)을 기간별로 누적 합산하면 됨.
- "메인페이지도, 분석페이지도 누적율은 이 로직으로 잡으면 될 거 같다" = 메인탭 Due Date 기준의 `isDue`/`isDone` 판정 로직을 그대로 재사용해서, 분석탭 누적도 여기 맞춰라.

**교체할 함수**: `report_builder.py`의 `dueDateRecordsByStage()` / `withCumulative()` (현재 confirmPeriod 캐치업 로직 들어있음, 이거 지우고 아래처럼 단순화):

```js
// 누적용 원자료: due 기간별로 묶되, "정시냐"가 아니라 "지금 됐냐"만 본다.
// due 없이 이미 완료된 건(라벨/ETD 누락, ~26개)은 주차별 표를 오염시키면 안 되니 기준일 기간에만 합류.
function cumulativeDoneRecordsByStage(rawRows, offsets, todayIso, period) {
  const records = {FIT: [], PP: [], TOP: []};
  for (const row of rawRows) {
    for (const stage of STAGES) {
      const due = resolveDue(row, stage, offsets);
      const isDone = row[`${stage.toLowerCase()}_done`];
      if (due) {
        if (due > todayIso) continue;
        records[stage].push({period: periodLabel(due, period), done: isDone});
      } else if (isDone) {
        records[stage].push({period: periodLabel(todayIso, period), done: true});
      }
    }
  }
  return records;
}

// 기간 순서대로 그냥 단순 런닝 합계(누적). 캐치업/confirm_date 비교 없음.
function withCumulativeDone(records, sortedPeriods) {
  const result = {};
  STAGES.forEach(st => {
    result[st] = {};
    let cumDone = 0, cumTotal = 0;
    sortedPeriods.forEach(p => {
      const inPeriod = records[st].filter(r => r.period === p);
      cumDone += inPeriod.filter(r => r.done).length;
      cumTotal += inPeriod.length;
      result[st][p] = {cumDone, cumTotal};
    });
  });
  return result;
}
```
(필터를 매 기간 돌리는 게 아니라 미리 기간별로 그룹핑해두는 게 더 낫지만, 데이터량 작아서 이대로도 무방. 다듬어도 됨.)

표시값: `누적 = cumDone / cumTotal`. **이 값의 마지막(최신) 기간 숫자가 메인탭 "Due Date 기준" 값이랑 100% 똑같이 나와야 정상** — 같은 `isDue`/`isDone` 로직을 기간별로 쪼갠 것뿐이라서.

이전에 있던 `effectiveConfirmDate` 기반 `onTime`/`confirmPeriod` 캐치업 계산은 누적에서는 이제 안 씀. 단, `effectiveConfirmDate`/`dueDateOnTimeComplianceByStage`는 **주차별(정시) 컬럼용으로 계속 필요하니 지우지 말 것.**

### 2. sec1 오른쪽 도넛

누적 계산에서 confirm_date 비교(`onTime`) 자체를 안 쓰게 되니 그 버그 클래스가 통째로 없어짐. 주차별(정시) 컬럼 쪽 `dueDateRecordsByStage`의 `onTime` 계산에는 `isDone` 체크가 필요한지는 별개로 한 번 더 확인은 해두면 좋음(정시 여부 판단이니 "승인 완료 상태에서 그 날짜가 due 이내"가 맞는 정의).

### 5. 개념 정리 — 헷갈리지 말 것
- **주차별 승인율 = 정시 승인율**: 그 주 due 안에 승인됐냐. 늦게 승인되면 그 주차 숫자는 영구히 미준수로 고정(안 바뀜).
- **누적 승인율**: "정시" 여부 상관없이 그냥 지금까지 승인(완료)된 비율의 누적. 메인탭 Due Date 기준과 동일 로직.
- 이 두 개는 원래 다른 숫자가 정상이고(주차별 정시 미달성 있어도 누적 완료율은 결국 100%로 감), 사용자도 이 구조는 최종적으로 동의함.

## 화면별 계산식 정리 (현재 코드 기준, 2026-08-02 세션 종료 시점)

공통 용어:
- `due` = `resolveDue(row, stage, offsets)` → DUE_DATA(2)/Supabase 고정값 있으면 그거, 없으면 `row.label`을 기준표(`offsets`)에서 찾아 `row.etd - 오프셋일수`로 계산. 라벨도 없거나 ETD도 없으면 `null`.
- `isDone` = `row.fit_done` / `row.pp_done` / `row.top_done` (원본 엑셀·Supabase의 완료 플래그, round 데이터와 별개 컬럼)
- `confirm_date` = FIT TRACK CHART 각 회차 블록의 "전달일"(없으면 Approved인데 전달일만 빈 경우 피팅일로 폴백). `effectiveConfirmDate()`가 FIT 생략(보정→PP직행) 케이스는 보정 승인일로 대체.

### 1. 메인탭 표 — "전체 스타일 수 기준" 컬럼
`computeProgressFromRaw()`. due 여부 상관없이 무조건 카운트.
```
total_all = 그 stage 적용되는 전체 스타일 수
total_done = isDone인 것 카운트
표시값 = total_done / total_all
```

### 2. 메인탭 표 — "Due Date 기준" 컬럼
같은 함수, `isDue` 필터링 후.
```
isDue = (due && due <= asOfDate) || (!due && isDone)   ← due 없어도 이미 끝난 건 포함(오늘 추가한 부분)
baseline_all = isDue인 것 카운트
baseline_done = isDue && isDone 카운트
표시값 = baseline_done / baseline_all
```
`isDue && !isDone`인 건은 `bucket.overdue[]`에 담겨서 "미완료 상세" 드릴다운에 표시됨(due, status, 이전 단계 활동, 초과영업일 등).

### 3. 분석탭 sec1 — "단계별 Due Date 달성률" 도넛 6개
왼쪽(누적 완료율) = `analysisStats()`의 `byStage[stage]`, 계산식은 위 2번(Due Date 기준)과 동일한 `isDue` 로직.
```
표시값 = byStage[stage].done / byStage[stage].total
```
오른쪽(누적 정시 승인율) = 아래 4번 "누적" 표의 **가장 마지막 기간(주/월)** 값을 그대로 가져다 씀. 별도 계산 안 함(어제까지는 "주차별 평균"으로 다르게 계산해서 숫자가 안 맞았음 — 지금은 통일시킴).

### 4. 분석탭 "주별 정시 승인율" 표 — 핵심, 제일 복잡함
`dueDateRecordsByStage()`가 원자료를 만들고, `dueDateOnTimeComplianceByStage()`(주차별용) / `withCumulative()`(누적용)가 각각 다르게 집계함.

**원자료 생성** (`dueDateRecordsByStage`):
- due 있는 스타일: `{duePeriod: due가 속한 주/월, confirmPeriod: 승인일이 속한 주/월(없으면 null), onTime: isDone && confirmDate && confirmDate<=due, hasRealDue: true}`
  - ⚠️ **`isDone` 체크를 오늘 뒤늦게 추가함(검증/배포 안 된 상태로 세션 종료)**. 이거 없으면 최신 회차가 Rejected인데 전달일만 있어도 "정시 승인"으로 오판돼서, 완료 건수보다 정시 건수가 더 많아지는 모순 생김(PP 402완료/407정시로 실측 확인됨).
- due 없는데 isDone인 스타일: `{duePeriod: null, confirmPeriod: 기준일이 속한 주/월, onTime: true, hasRealDue: false}` (라벨/ETD 누락 케이스, 26개 정도 있음)

**주차별(고정값) 컬럼** (`dueDateOnTimeComplianceByStage`):
```
hasRealDue인 것만, duePeriod별로 그룹
표시값 = 그 주 due였던 것 중 onTime인 것 / 그 주 due였던 것 전체
```
한 번 due 주차에 "미준수"로 찍히면 나중에 승인돼도 이 숫자는 안 바뀜(영구 고정). due 없는 26개는 여기 안 들어감(안 그러면 최신 주차에 몰려서 카운트 부풀려짐 — 실제로 한 번 이 버그 냈다가 고침).

**누적 컬럼** (`withCumulative`):
```
그 기간 p까지:
  cumTotal = (hasRealDue && duePeriod<=p인 것 개수) + (!hasRealDue && confirmPeriod<=p인 것 개수)
  cumOnTime(승인 완료 누적) = (hasRealDue && duePeriod<=p && confirmPeriod!=null && confirmPeriod<=p인 것 개수) + (!hasRealDue && confirmPeriod<=p인 것 개수)
표시값 = cumOnTime / cumTotal
```
"주차별"과 근본적으로 다른 개념: due 기준이 아니라 **"실제로 승인이 일어난 시점"** 기준으로 채워짐. 밀렸던 게 나중에 승인되면, 승인된 그 주차의 누적에 반영되면서 따라잡음. due 없이 완료된 26개는 기준일 시점에 한 번에 합류.

### 5. 분석탭 "협력사/아이템/TD/QA별 평균 초과 영업일" 바 차트
`analysisStats()`의 `groupOverdueDays` / `groupOverdueDaysByStage`.
```
대상: isDue && !isDone인 건들만 (즉 "기준일 지났는데 아직 미완료")
days = businessDaysSince(due, asOfDate)  ← 영업일(주말 제외) 기준
그룹별 표시값 = 그 그룹의 days 평균 (반올림). 초과 건 자체가 없는 그룹은 0
```
